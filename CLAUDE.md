# KH Golf Shot Tracker

A phone-first web page that tracks golf shots for Matthew's family. GitHub Pages serves it from `main`. The page reads the data files every time it loads, so updating a file updates the site.

## Players and data files

`data/players.json` lists the players (and `DEFAULT_PLAYERS` in `js/app.js` repeats it, for a phone's first visit). Each player has their own data file in the same format:

| Player | id (URL `?player=`) | File | About |
|---|---|---|---|
| Dad | `dad` | `data/dad_golf_data.json` | 56, 6′1″; has had lessons and knows the basics; older Lynx Black Cat irons (3 iron to PW), Callaway Edge 5 hybrid and driver |
| M2 (Matthew) | `matthew` | `data/matthew_golf_data.json` | Matthew himself. Six August 2026 sessions from his own file (Rapsodo and Toptracer, partly filled: twelve 9 iron carries, single best shots for the 7 iron and driver), plus his swing notes. Callaway Edge irons, regular flex, confirmed only for Aug 5. Also his Toptracer games from May 1–3, 2026 (early summer), and a yardage chart for his whole bag (Nov 25), which the game plays until new range sessions replace it. On his page, photos and videos go straight to Claude |
| M3 (Matthew's brother) | `brother` | `data/brother_golf_data.json` | 14, 5′0″; has had lessons and knows the basics; plays for fun and wants to keep up with his friends on the team |

If it isn't clear whose photos they are, ask Matthew before adding anything.

A player's clubs are in the `equipment` block of his file: `equipment.bag` has one entry per club with its `model` and `loft_deg` (use `null` when the loft isn't known). Each loft sets that club's launch target, so when Matthew says a player has new clubs or gives their lofts, update the bag and leave the shot data alone.

The page itself also commits to `main`: on a phone with a GitHub key, every goal change is saved straight into that player's data file ("Update Dad’s goals from the tracker"). So run `git pull origin main` before editing any data file, and pull again if a push is rejected.

## Adding shots from a photo of a range screen

Dad or M3 takes photos of the Toptracer or Rapsodo screen and texts them to Matthew, who sends them here (with his own, for M2) and asks for them to be added. Follow these steps.

1. **Read every row.** Toptracer's "All shots" screen has these columns: Time, Club, Flat carry (yds), Total (yds), Ball speed (mph), Launch (deg), Apex (ft), Landing (deg), Curve (ft), Offline (ft). Some screens also show Hang time (s).
   - Arrows: ◀ before a number means left (store it negative). ▶ after a number means right (positive). A bare 0 is 0.
   - Store values the screen doesn't show (no column, "-", blank) as `null`. Never guess a number you can't read clearly. Ask, or leave the row out and say so.
   - Record the club the screen shows, using these names: `PW`, `GW`, `SW`, `LW`, `9i` to `4i`, `5hy`/`4hy`, `3w`/`5w`, `Driver`. Toptracer shows "Sw", which becomes `SW`; "Pw" becomes `PW`; "5w" stays `5w`. Change a club only when Matthew says it was mislabelled.
   - Times are 24-hour `HH:MM`, so "01:00 PM" becomes `13:00`.
   - Keep every shot, including topped or fat ones. The page spots likely mis-hits by itself, leaves them out of the averages and shows them as hollow dots. It also spots outliers, solid shots far off a club's usual carry: they're left out of the averages too but still count as solid contact, and show as ringed dots. And it spots a warm-up (fat-looking wedges in the first few minutes) and leaves it out of everything. Never delete or skip a real shot to make the numbers look better.
   - When Matthew says some balls weren't full swings (drill balls, half swings, a warm-up), add `"partial": true` to those shots, so they're kept out of the full-swing numbers. Never add it on a guess.
2. **Pick the session.** Screens show times but not dates. Use the date Matthew gives. If he gives none, ask; photos can arrive days after the range session.
   - If that player already has a session for the same date and venue, add the shots to it.
   - Otherwise create a session with id `{date}-{device}` (e.g. `2026-11-15-toptracer`). Give it `date`, `device`, `bay` or `location` if known, `shot_level_data: true`, `metrics_not_available` and `notes`, copying the shape of the existing sessions.
   - Overlapping screenshots are common. Skip any row the session already has: the same time and club with every number the same. Two shots in the same minute can share carry, total and ball speed (Nov 10's PW shots 008 and 009 do), so check every column before skipping one. `check-data.js` warns about rows that repeat in every column.
   - Leave `baseline_session_id` alone. Dad's is his Aug 2026 Rapsodo session. M3's is `null`, which makes the page use each club's first session.
3. **Write the shots in time order.** Screens list the newest shot first, so reverse them. In an existing session, ids continue its sequence (e.g. `2026-11-01-049` after `2026-11-01-048`). A new session numbers its shots `{session id}-001`, `-002`, … (e.g. `2026-11-15-toptracer-001`), the same as the page does, so two sessions on one day never share an id. Use the same keys as the existing shots: `id, time, club, carry_yds, total_yds, ball_speed_mph, launch_deg, apex_ft, landing_deg, hang_time_s, curve_ft, offline_ft`. Add `club_speed_mph`, `spin_rpm` or `smash_factor` only when the device shows them, and `partial: true` only when Matthew says a ball wasn't a full swing. Add any new club to that player's top-level `clubs` map. If the photo cuts off rows, add a line to the session's `notes`.
4. **Check before committing.** Re-read your rows against the photo one more time. Then `node scripts/check-data.js` (it checks every player's file) and `node tests/core.test.js` must both pass.
5. **Commit and push to `main`.** Matthew, the repo owner, approved pushing data updates straight to `main`, because that branch is what the website serves. If your session requires a different branch, ask once whether to push to `main`. Use a commit message like "Add 12 shots for Dad from 2026-11-01 (SW, 5w)". The site updates about a minute after the push.
6. **End with a short summary Matthew can forward:** shots per club, average carry per club (solid shots), each club's typical carry and pure-strike carry from the Practice tab's "Your yardages", how many likely mis-hits, outliers and warm-up or half swings there were, which clubs the page now marks "Needs work" (and any that dropped off the list), and anything notable, such as misses to one side or a club that went farther than last time. Use plain words, short and encouraging. Both have had lessons and know the basics, so skip beginner advice (grip, posture, ball position); for M3, keep it fun.

## Yardage charts

A player's `yardage_chart` is how far each club goes from an estimate or a fitting, not a range session (README, "Data format"). M2's came from a chat with Claude, which Matthew says is very close to what he really hits.

- Never turn a chart into shots, and never add its numbers to a session. None of the stats use it. The Practice tab lists it, and the Game tab plays it for each club until a range session from the chart's `date` on has that club.
- When Matthew sends a new chart, replace the whole `yardage_chart` and set its `date` to the day it's added. Keep `[low, high]` where the chart gives a range. Put any loft it gives (like "GW (52°)") in `equipment.bag`, and add any new club to the `clubs` map.
- `node scripts/check-data.js` checks it.

## Adding or updating goals

Each player file has a `personal_goals` list. The page pins the open ones at the top of every tab as a constant reminder.

- When Matthew asks for a goal ("add a coach goal for Dad: keep your head still"), append `{ "id": "goal-YYYY-MM-DD-N", "text": "...", "source": "coach", "added": "YYYY-MM-DD", "done": false }` to that player's `personal_goals`. Use `"coach"` for anything a coach or teacher gave him and `"me"` for his own goals. Use today's date and the next free N for that day.
- Keep the text short and in Matthew's words: something the player can read at a glance, ideally under 80 characters (the check warns past 140). Don't reword or merge goals.
- To mark a goal achieved, set `"done": true` rather than deleting it; the page moves it to a "Done" list. Delete only when asked.
- Then run the checks, commit (e.g. "Add a coach goal for Dad") and push to `main` as above.

## Swing reviews from a video

Matthew may send a swing video and ask for a review. The page shows it under Practice → Swing: the key frames with lines drawn on them, numbered notes, what's working, and the fixes linked to drills.

1. **Ask what isn't clear:** whose swing, the date, the club, and the view (face-on, or down the line from behind the hands). Never commit the video itself.
2. **Privacy:** the repo and the site are public. Before a player's first review, ask Matthew whether to blur faces (recommended for M3, who is 14), and use `--blur` when he says yes.
3. **Find the frames:** `python3 scripts/swing-frames.py probe VIDEO`, then `python3 scripts/swing-frames.py sheet VIDEO --out /tmp/sheet.jpg --every 0.05` and look at the sheet to find setup, the top of the backswing, impact and the finish (plus any frame that shows a problem best).
4. **Pull them out:** `python3 scripts/swing-frames.py extract VIDEO --out media/<player id>/<review id> --at 0.42:address,1.10:top,1.36:impact,2.05:finish` (add `--blur X,Y,W,H` for a face; `N:X,Y,W,H` for frame N only). The review id is `{date}-{club}-{view}`, e.g. `2026-11-15-7i-face-on`. It prints the `frames` JSON to start from.
5. **Mark them up:** look at each frame (`python3 scripts/swing-frames.py grid FRAME --out /tmp/grid.png` shows pixel coordinates). Mark only what is clearly visible, and say so when the camera angle makes something hard to judge. Never guess.
   - Marks: `type` is line, arrow, circle, box, angle, path or dot; `kind` is issue (orange), fix (green), good (blue) or ref (white guide); points are `[x, y]` in frame pixels; `dash: true` for guide lines; `label` up to 24 characters; `n` numbers a mark and matches the note with the same `n`.
   - Useful marks: a dashed line through the head at address, repeated on later frames to show head movement; the spine or shaft angle (`angle`); the hands against the ball at impact; the shaft plane down the line; a balance line at the finish.
6. **Write the review** into that player's `swing_reviews` list: `id, date, session_id` (if it matches a range session), `club, view, title, summary, video` (`duration_s`, `fps`), `frames` (each with `src, w, h, time_s, label, marks, notes`), `good` (short strings) and `fixes` (`{ "text": "...", "drill": "contact:0" }`; the drill is `focus id:drill number` in `js/tips.js`, so `contact:0` is the Towel drill). Keep the words short and encouraging, like the shot summaries.
7. **Check:** `node scripts/check-data.js` and `node tests/core.test.js` must pass. Then run `node scripts/review-preview.js <player id> <review id>` and look at every PNG to make sure each mark sits where it should.
8. **Commit and push** the frames and the data change to `main` ("Add a swing review for Dad: 7 iron, Nov 15"), then end with a short summary Matthew can forward: what's working, the one or two things to fix, and the drills for them.

## Coach videos and drill animations

Each drill in `js/tips.js` has `art`, its frames for the animation (`js/drillart.js` lists the scenes, poses and marks; 2–4 frames, captions up to 60 characters), and `video` when a coach's video has been found: `{ "id", "title", "by", "note" }`.

- Only use a YouTube id copied from a real search result or page. Never type one from memory or make one up.
- The listing must show the same drill (or the same skill) and come from a channel with a long track record of good instruction, such as Titleist, Rick Shiels, Me and My Golf, Danny Maude, Golf Monthly, Golf Digest, Golf Channel's School of Golf, PGA of America, or U.S. Kids Golf for juniors (or a nationally known teacher, such as a GOLF Top 100 Teacher). The videos can't be watched from here, so the channel's track record is the check. If you can't tell, leave `video` out; the page then shows a "Look it up on YouTube" search instead.
- When Matthew says a video is wrong or doesn't play, replace it or take it out.
- `node scripts/check-data.js` checks every drill's animation and video.

Don't change `coaching_notes` or the tips in `js/tips.js` unless asked. Don't commit the photos themselves unless asked, because the repo is public.

## Courses for the Game tab

The Game tab plays real courses with each player's own range shots (see README, "Game"). Matthew wants popular, well-known courses: pick those when choosing the next one. Rounds are saved on each phone, not in the data files, so there's nothing to commit after a round. To erase a player's rounds on every phone (say, test rounds), set `rounds_reset` in his data file to today's date (`YYYY-MM-DD`): each phone erases his rounds from that day or before the first time it loads the file. M3's is set to 2026-11-25. On one phone, "Erase all rounds" under Your rounds does it too.

- The courses: TPC Harding Park and Edgewood Tahoe. `js/courses.js` holds each one's scorecard: par, each set of tees' yardage for every hole, a short note from the course guides (checked against the map), and its sources. Its map and heights are files of their own, loaded when a round on it starts (`GolfCourses.load`), so the page doesn't fetch every course on every visit; the course of a round in progress and the one picked last are prefetched soon after the page opens (`gmPrefetch`), so a round plays with no signal at the range. `node scripts/stamp.js` stamps their addresses in `js/courses.js`, and a new course needs its two files in `FILES` (a test checks).
- `js/courses/COURSE.js` holds a course's ground, as mapped in OpenStreetMap (© OpenStreetMap contributors, ODbL): the boundary, the lake beyond it, every hole's line of play, green, fairway, tee box, bunker and pond, and the trees. It's built by `python3 scripts/build-course-map.py COURSE FEATURES.geojson BOUNDARY.json [--tiles DIR]` from OSM's data for the course (each course's settings are `COURSES` in the script, and its gaps are filled by its hooks); don't edit it by hand. The page credits OpenStreetMap wherever the map shows, as the licence asks: keep that line. The script takes the spikes out of OSM's outlines (`despike`), builds the fairways OSM lacks down each line of play, shaped like the mapped ones (`build_fw`; `fairwaysBuilt` lists them; if OSM gains them, drop them from it), and gives each fairway a spine (`fairwaySpine`: its hole's line of play, corners rounded) that its mowing stripes run square to. The game rounds the outlines' corners when it loads them (`rounded` in `js/game.js`), so leave them as OSM has them. Its input is the OSM cache in `ummerr/mackenzie` (see the script); refreshing it needs network access to OSM, which this environment doesn't allow by default.
  - Harding Park: OSM's 27 hole lines are Harding's 18 and the Fleming nine (`lines`). Seven holes (2, 4, 5, 7, 9, 13, 15) have no fairway in OSM. The 9th green isn't in OSM either: the script builds one round the end of its line, between its front bunkers (`greensBuilt`); if OSM gains it, the script uses OSM's. The 18th has no line in OSM, so one is built across the inlet; the 16th's and 18th's lines follow the middle of their fairways (`follow_fw`); the 13th's passes left of its fairway bunker (the 2020 PGA Championship guides put it down the right); the 18th's forward tees may sit well to the side of its line (`tee_off`); and the 4th's large cypress stands inside its dogleg. Lake Merced is beyond the boundary from vertex 34 round to 12.
  - Edgewood Tahoe: OSM's 18 lines carry their numbers (`lines: 'ref'`); OSM has the 17th as a par 4, but the card and every guide make it a par 3. Holes 4 and 14 have no fairway in OSM. Lake Tahoe is beyond the west side (boundary vertices 10 to 20), where the USGS heights 15-30 yds out are the lake's surface, past a strip of beach; OSM's water inside the boundary (the ponds and Edgewood Creek) plays as penalty areas. Its trees are pines (`treeKind`). At 6,250 ft (`altitudeFt` in `js/courses.js`) the ball carries about 7% farther (Titleist's rule of thumb, `AIR_K` in `js/game.js`), and the game's club numbers, power and aim allow for it.
- `js/courses/COURSE-elev.js` holds the ground's height every 6 yds, from the USGS 3D Elevation Program (public domain) via the AWS Terrain Tiles, written by the same script with `--tiles DIR` (the zoom-15 terrarium tiles over the course; the script says where to get them; this environment can fetch them). Heights are stored up from each course's `elev_base`. The page credits USGS 3DEP next to OpenStreetMap: keep it. The greens are level on purpose, for putts and for a ball rolling on one; don't add slopes to them from these heights, which are too coarse for a green.
- Use only yardages from a real scorecard or the course's own site, and never estimate one. Leave out any set of tees whose hole-by-hole yardages can't be found. The Red and Gold tees at Harding Park are left out for that reason. Edgewood's Blue and White are GolfPass's card (the same as Greenskeeper.org's), checked against the mapped tee boxes.
- When Matthew sends a photo of a scorecard (say, for the forward tees), add the tees to `tees` and each hole's `yds`. The game stands them on the line of play at their yardage; to put them on their real tee boxes, add their yardages to the course's `yds` in `scripts/build-course-map.py` and rerun it. `node tests/core.test.js` checks that they add up and that every tee is within 12 yds of its yardage.
- A new course: pick a popular one whose holes OSM maps (the `ummerr/mackenzie` cache has 82; most need network access to OSM), get its real scorecard, add its settings to `COURSES` in the script (and hooks for its gaps), its scorecard to `js/courses.js` (with its two files in `FILES`), and tests like Edgewood's. Then render every hole and check it against the course guides before shipping it.

## Reading the Rapsodo screen live

On a Mac with the iPad mirrored to it (QuickTime or AirPlay), the Game tab's **From the range** reads each shot off the Rapsodo screen by itself and plays it (README, "Reading the launch monitor's screen"). The boxes round each number are saved on that Mac, not in the data files, so there's nothing to commit after setting it up.

- When Matthew sends a screenshot of the screen, check the reader against it: `python3 scripts/swing-frames.py grid IMAGE --out /tmp/grid.png` shows pixel coordinates, then `node scripts/live-read.js IMAGE carry=X,Y,W,H total=… side=… speed=…` prints what each box reads. If a number misreads, fix it in `js/live.js` and add a test for it. Don't commit the screenshot.
- After changing `js/live.js`: `node scripts/stamp.js`, `node tests/core.test.js` and `node scripts/live-check.js` (which plays a pretend Rapsodo screen into the game end to end).
- `vendor/tesseract/` is Tesseract.js 7.0.0 with tesseract.js-core 7.0.0 (the SIMD, LSTM-only build) and the English model `4.0.0_best_int` from @tesseract.js-data/eng 1.0.0, all Apache 2.0 with their licences. Don't edit those files. To update them, replace all of them from matching versions, then run the checks above.

## Code

- `index.html`: markup and styles. `js/app.js`: the UI. `js/core.js`: stats, the mis-hit and outlier rules, rounding and the paste parser; the node tests load it too. `js/tips.js`: the Tips & drills content for each player, shown under the Practice tab (the tab's internal id is still `tips`; its sections are Range, Swing and Drills). `js/drillart.js`: the drill animations. `js/review.js`: swing review markup and its checks. `js/flight.js`: the Stats tab's shot replay (each shot's flight rebuilt from its numbers, the course, and the tee box, side and green cameras); it needs nothing beyond the usual shot keys, so there's nothing extra to record. It also draws the Game tab's holes. `js/courses.js`: the Game tab's courses (scorecards; each course's map and heights are in `js/courses/`, loaded when it's played). `js/live.js`: the screen reader (reading the OCR's text, the checks, spotting a new shot and cleaning up each box are pure, so the tests load it; the capture and the OCR run in the browser, with Tesseract from `vendor/tesseract/`). `js/game.js`: the game's engine (the holes on the ground, his real shots for each club, the real swing: reading a swipe, or the phone's gyroscope when he swings the phone (`readMotion`), his clubs' face and path from their shots, the ball-flight laws and the strike; the shot types (`SHOTS`: draw, fade, high, low, spinner, chip, flop, splash, punch) and the one a golfer would play from each spot (`suggestShot`, which the page doesn't show: Matthew wants every shot to start as the plain one, aimed straight at its target rather than aimed off for the player's usual shape, with the player choosing any shape and aim himself and no shape named before the shot); the swing meter's timing, penalties, putting, the score). Each club's face and path come from its shots' offline and curve, so new range sessions change how the game's swing flies with nothing else to update.
- Scripts: `scripts/swing-frames.py` pulls frames from a swing video; `scripts/review-preview.js` screenshots a review's frames as the page draws them; `scripts/live-check.js` checks the screen reader end to end; `scripts/live-read.js` reads a screenshot of a launch monitor the way the reader does.
- Tests: `node tests/core.test.js`. Data check: `node scripts/check-data.js`. After changing any file under `js/`, run `node scripts/stamp.js` (it stamps the script tags in `index.html` so phones fetch the new files; the tests fail until it's run).
- `index.html` sets a Content Security Policy: no inline scripts or event handlers (`onclick=`, `onerror=`), and anything new from another site (a font, an image host, an API) has to be added to it. It allows WebAssembly (`'wasm-unsafe-eval'`) and same-site workers for the screen reader's OCR. The motion swing can't be tried on a real phone from here, so the tests swing a phone by numbers (`phoneSwing`) and check what `readMotion` reads back.
- Preview: run `python3 -m http.server 8000` in the repo root and open http://localhost:8000 (add `?player=brother` for M3).
